The technician's compliance flow: from a score to a fix to proof

A proposal for how a technician discovers, explores, navigates and audits configuration compliance in ServiceOps, built on the CIS research and on the Patch and Package patterns our users already know.

Summary

In one minute

  • What we have: four technician pages (Dashboard, Benchmark, Compliance Policy, Endpoints) that tell a technician how compliant the estate is.
  • What is missing: the path from that number to the exact machine and rule, the reason it matters, the fix, and the proof. Today a failed rule is a dead end.
  • The proposal: make the Compliance Policy the technician's home. Open it as the same full-screen detail drawer as a Patch Deployment, and drill Policy → Endpoint → Rule in at most two clicks. Every failure gets the same four actions: Deploy fix, Create change, Create task and Request exception. Every scan becomes exportable evidence.
  • Why us: scanners find problems; ServiceOps already owns the endpoints, the people, approvals and the deployment engine that fixes them. This is the join competitors lack. In the research, ManageEngine, NinjaOne and Tanium have no exception workflow, and the scanners have no deployment engine.
01

Problem statement

Problem

Technicians can see that a policy is 83% compliant, but cannot quickly answer the four questions that follow: which machines are failing, which rules, why it matters, and what to do next. Fixing and proving compliance happens outside the product, in spreadsheets, emails and one ticket per machine.

What this costs the organisation today

  • Results are a dead end. A failed rule has no owner, no action and no status, so the same failures reappear scan after scan.
  • Fixes don't scale. One rule failing on 120 laptops becomes 120 tickets, or nothing. The deployment engine that could push one fix to all 120 sits one module away, unconnected.
  • Nothing can be waived properly. When a rule genuinely can't be applied, such as a legacy printer that needs an old protocol, there is no approved, time-limited exception. The failure either drags the score down forever or gets ignored.
  • Audits are manual. An auditor asks "prove these servers were compliant in March". The answer is screenshots and exports stitched together by hand, with no record of which benchmark version was used or who approved which exception.
  • The nested structure is hard to navigate. A policy holds endpoints, each endpoint holds hundreds of rule results, and each rule carries CIS metadata. Without a clear drill-down, technicians get lost three levels deep and lose the context they started from.
02

Goal statement

Goal

From any compliance number, a technician reaches the exact endpoint and rule in two clicks, understands why it matters in plain words, and starts a fix with ServiceOps' existing deployment, change or task tools in one more. Every result stays provable to an auditor without IT's help.

Four design principles: discover, explore, navigate, audit

PrincipleWhat it means for the technicianHow the flow delivers it
Discover"What needs my attention right now?" without hunting for it.Dashboard KPIs and charts all click through to a pre-filtered list. Failed-first sorting everywhere. A "New since last scan" (drift) filter. Expiring exceptions are surfaced.
ExploreUnderstand a failure in plain words before touching anything.Each rule reads in CIS order: what, why, what it costs, how to check, how to fix. Evidence shows expected vs found. Level, severity and Automated/Manual appear as pills.
NavigateMove between policy, endpoint and rule without losing the starting point.One drill pattern: drawer → tab → side panel, with a breadcrumb. Three entry points (policy, endpoint, rule) lead to the same result card. At most two overlays. Every level has a link.

One shared status language

Every screen uses the same six states, so a result reads the same wherever it is met.

PassFailManual checkExceptedNot applicableNot reached

Score = passed ÷ (passed + failed), shown with its denominator, for example "91% · 2,548 of 2,800 checks". Excepted, not-applicable and manual results are left out of the denominator and counted beside it. The same formula rolls up per endpoint, per policy and per benchmark.

The nested policy flow: who needs it, and how to show it

The policy is the only record that holds all four levels at once (policy → endpoints → benchmark rules → rule metadata), so it is where navigation can go wrong. First, who uses each level:

LevelRohan · TechnicianAnanya · AdminVikram · Auditor
Policy (score, trend, scope)DailyWeekly, by benchmarkAt audit time
Endpoints in the policyDaily: worst machines firstRarelySampling
Rules in the policyDaily: biggest fix first (one rule × many machines)To judge a rule's impactSampling
Result + rule metadataBefore every fixWhen approving exceptionsEvidence
Takeaway: the technician needs the deep levels most and uses two lenses on the same data. "Worst machine first" is used when one machine is the problem. "Biggest rule first" is used when one fix clears 120 machines, and that is where the real time saving is. The policy detail must offer both, side by side, as tabs.

Three ways to show the nesting

A · Page-by-page drill

The prototype at 5177: policy page → device page with a breadcrumb → rule side panel.

+ Simple, matches the mental model.
− Only one lens (by device). Each level replaces the last, so context is lost. New pattern for ServiceOps users.

B · Drawer, tabs, side panel Recommended

The policy opens as our standard full-screen detail drawer, like a Patch Deployment. Endpoints and Rules tabs. A row opens a side panel that drills one level more, with back and a breadcrumb.

+ Both lenses. Policy context stays visible. Same muscle memory as Patch and Package. Drawer tabs keep several policies open. − Needs care so the side panel does not stack twice.

C · Matrix (endpoints × rules)

A heat-map grid of every endpoint against every rule.

+ Great overview for auditors and for spotting a rule that fails everywhere.
− Unreadable at hundreds of rules. Best as an extra view in Phase 3, not the primary flow.

Recommended structure (option B)

Exists in the prototype patternNew tabs proposed

Navigation rules that keep it shallow

  1. Two clicks to evidence. Policy drawer → row (Endpoint or Rule) → result. Never more.
  2. One side panel, never two. Drilling inside the panel replaces its content and adds a breadcrumb (CP-101 › EP-204 › 5.2.5) and a back arrow. This is the same in-panel step the Form Rules "How do I resolve" page uses.
  3. Leaving the policy is explicit. "Open endpoint" or "Open rule" opens that record as a new drawer tab, so the policy tab stays put and the technician can return.
  4. Failed first, always. Sections, endpoints and rules sort by failures and severity. Passing items fold away behind a count.
  5. Every level has a link. For example #/compliance-policies/CP-101/endpoints/EP-204, so a technician can paste a finding into a ticket or chat.

Page by page

What each page shows today and what changes. Everything reuses components we already ship: the listing grid, the full-screen detail drawer and its tabs, the side panel, the header KPI strip, approvals and the audit trail.

1 · Dashboard

"Where should I act today?"

Shows
  • Score with its denominator, and the trend against a target set by each customer (not a fixed 85%).
  • Failures by severity · Top failing rules (biggest fix first) · Top failing endpoints.
  • New failures since last scan (drift) · endpoints not reached.
  • Exceptions expiring in 30 days · open findings without an action.
Changes

Every number and bar is clickable and opens the right page pre-filtered. A "My policies" switch lets a technician see only the policies they own.

2 · Benchmark (rule lens)

"What does this rule mean, and where does it fail?"

Listing

Benchmarks with OS, version, level, score across policies and number of policies using it.

Benchmark detail

Overview (version, "based on CIS …", score) · Rules (sections, failed first) · Policies using it · Endpoints.

Rule detail tabs
  • Summary: what, why, what it costs, in CIS order.
  • Check & fix: the audit procedure, the remediation and the default value.
  • Where it fails: failing endpoints grouped by policy, with bulk Deploy fix.
  • Used in: policies and benchmarks that include this rule.
  • References: CIS Controls, NIST, PCI and other framework mappings.

Read-only for technicians; editing stays with the admin.

3 · Compliance Policy (job lens, home)

"Is my job running, and what did it find?"

Listing

List & KPI (default) or Tiles. Row actions: Run now · Schedule · Edit · Clone · Delete. Saved views such as Non-compliant, Not scanned and Mine.

Create

The existing full-page form: name, one benchmark, endpoints, schedule, notify. New: optional pilot group first ("test on 5 machines, then roll out"), as CIS advises.

Detail

The drawer in section 06: Overview · Endpoints · Rules · Findings · Exceptions · Scan history · Audit trail.

4 · Endpoints (machine lens)

"Is this machine safe across every policy?"

Listing

Score, failed critical, policies applied, last scan, drift, agent health.

Endpoint detail

The existing Endpoint drawer gains a Compliance tab beside Vulnerabilities, BOM, Patches and Deployment. It uses the Patches tab's pattern: Failed Passed Excepted Manual pills, a policy filter, and Take action on selected rows.

Why here

A technician fixing one machine sees missing patches, vulnerabilities and misconfigurations together, on one page they already use.

The fix loop: where ServiceOps wins

Every competitor in the research runs the same loop. ServiceOps can close it inside one product, because the deployment engine, change management and approvals already exist.

Exception rules, from the research

  • Scope is one rule on chosen endpoints, never a whole section (Rapid7, Qualys).
  • A reason is required, chosen from: Risk accepted · Awaiting maintenance window · Fix unavailable · Mitigating control in place (ServiceNow's list).
  • Approval uses the ServiceOps approval engine. One or two levels is the leadership decision below.
  • Expiry is required. The finding re-opens at expiry, or earlier if a scan finds a different value (Qualys).
  • The raw result stays Fail. The view shows Excepted with the reason on hover, so nothing is hidden from an auditor.
09

Audit: making every result provable

Scan history (policy tab)

One row per run: date, benchmark version, scope (which endpoints), duration, score, and who triggered it. Opening a run shows that run's results as they were then, not as they are now.

Evidence export (per run)

PDF or CSV carrying the benchmark version, scope, timestamp, every result with evidence, and the exception register with reasons and approvers. The same scope and version reproduce the same answer.

Exception register

All exceptions across policies: rule, endpoints, reason, approver, approved on, expires, status. Filterable, exportable, and shown on the dashboard when expiring.

Audit trail

Who created, edited, enabled, ran and excepted, in our standard Audit Trail format. Read-only access for an auditor role.

Walkthrough: one Monday in Rohan's week

  1. DashboardThe score dropped from 96% to 91%. "Top failing rules" shows Screen lock after 15 min failing on 120 Windows 11 laptops, all new since Sunday's scan.
  2. Dashboard → Benchmark › rule 2.3.7.3One click opens the rule. Summary says why it matters. "Where it fails" lists the 120 laptops, all in policy CP-114.
  3. Rule → Where it fails → Deploy fixRohan selects all 120 and clicks Deploy fix. The existing deployment form opens with the remediation script and the 120 endpoints filled in. He schedules it for tonight.
  4. Policy CP-114 › FindingsThe 120 results now read Deploying · PKD-1023. Nobody re-types anything into tickets.
  5. Policy CP-114 › Endpoints › EP-377 › rule 18.4.2One Finance laptop also fails "SMBv1 disabled". The old cheque printer needs it. Rohan clicks Request exception: this rule, 12 Finance laptops, "Fix unavailable — printer replacement ordered", 90 days.
  6. Admin approval queueAnanya approves it. The 12 results show Excepted, and the raw Fail stays underneath.
  7. Tuesday, automaticThe deployment finishes and triggers a re-scan. Screen lock passes on all 120. The score is 97%.
  8. Quarter end · Scan history → Export evidenceVikram exports the run: benchmark version, the 300 laptops, every result, and the exception register with Ananya's approval. The audit request is answered in minutes.
  9. 90 days later, automaticThe exception expires and the SMBv1 failure re-opens by itself, so nobody has to remember.

Phasing: feasible steps, each one usable on its own

Sizes are relative (S, M, L), to be confirmed with engineering. Each phase reuses existing ServiceOps components.

Phase 1 · See it

Navigate & understand

Size: M · mostly front end

  • Policy drawer tabs: Overview, Endpoints, Rules, Scan history, Audit trail
  • Endpoint panel and rule panel with in-panel drill and breadcrumb
  • One result card with evidence and CIS fields
  • Six-state status and score with denominator
  • Compliance tab in the Endpoint drawer
  • Dashboard click-throughs, "My policies"

Delivers: discover, explore, navigate.

Phase 2 · Fix it

Act & govern

Size: L · needs back-end links

  • Deploy fix → pre-filled Package/Script deployment
  • Create change (affected CIs) · Create task (grouped)
  • Status written back · auto re-scan
  • Exceptions: request, approval, expiry, re-open
  • Findings and Exceptions tabs · exception register

Delivers: the ServiceOps difference.

Phase 3 · Prove it

Audit & scale

Size: M

  • Evidence export per run
  • Drift ("new since last scan", compliant since)
  • Benchmark version diff and opt-in upgrade
  • Auditor read-only role
  • Pilot group in policy creation
  • Matrix view · network-device policies

Delivers: audit-ready, enterprise scale.
