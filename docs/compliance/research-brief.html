Security Configuration Compliance: a research brief for the designer

How CIS Benchmark compliance works, who uses it, the end-to-end flow, how nine competitors model it, and what to change in our Rules, Benchmark and Compliance Policy screens.

1. The short version

Seven findings change the design. Every other section is the evidence behind them.

  1. A CIS rule is a documented recommendation with a fixed set of fields: Title, Assessment Status (Automated / Manual), Profile Applicability (Level 1 / Level 2), Description, Rationale, Impact, Audit Procedure, Remediation Procedure, Default Value, References. That list is the rule-detail panel. verified
  2. Tags are not the rule's identity, and neither is the CIS number. CIS says there is no standard numbering convention, a number only means something inside one benchmark version, and a number can be reused after a check is deprecated. SCAP content gives each rule its own stable ID and attaches the CIS number as a reference tied to one product version. verified The module needs an internal rule ID per OS version; the CIS number and tags are metadata.
  3. A benchmark is one product at one version with its own version number, such as Ubuntu 22.04 v2.0.0. CIS has no fixed release cadence. Every scan result should be stamped with the benchmark version it ran against. verified
  4. Level 2 is a superset of Level 1. L1 is safe to apply broadly; L2 is defence-in-depth that may hurt usability. A STIG profile has replaced the old Level 3. verified
  5. Every competitor runs the same loop: content catalogue, policy or benchmark, targets, scheduled assessment, per-endpoint and per-rule results with a compliance percentage, remediation, re-assess, and exceptions with an owner, a reason and an expiry. Our module has the first four stages. The last four are the gap. inference
  6. Exceptions are a first-class record, not a note. Every mature product scopes an exception to a rule and a host set, requires a written reason, routes it through approval, gives it an expiry, keeps the raw result untouched and shows the override in audit output. verified
  7. Remediation lands in ITSM as grouped work, not one ticket per failed check. ServiceNow groups failed results into Remediation Tasks and raises a Change from a task. Tanium pushes CIS remediation keyed to the same control IDs, then re-assesses. verified ServiceOps already has Patch, Package and Change, so the join is the design opportunity.

2. Domain knowledge, explained PM-to-designer

What a CIS Benchmark is

A consensus document, built in the community CIS WorkBench, that targets one product at one version and groups its recommendations into sections. The z/OS V2R5 benchmark v1.1.0 has 219 recommendations across 9 domains. verified Benchmarks are published once the community agrees and keep being maintained afterwards; new and updated benchmarks are announced by monthly email. verified The Windows benchmark for a release covers all earlier builds of it.

Licensing shapes the product

The free benchmarks are PDFs. The machine-readable XCCDF format, which automated checks come from, is for CIS SecureSuite members only. verified Every competitor owns that licence and ships CIS-derived content on its own schedule; ManageEngine syncs content to the server every day at 1 AM. So in our module the admin curates rule content. They do not author it.

Anatomy of one recommendation

This is the rule-detail panel, in reading order: what, why, what it costs, how to check, how to fix.

FieldWhat it answers for the reader
TitleThe intended configuration, in one line
Assessment StatusCan a scanner check this (Automated) or must a human (Manual)?
Profile ApplicabilityLevel 1 (everyone) or Level 2 (special security needs)
DescriptionWhat the setting is
RationaleWhy it matters: the threat it closes
ImpactWhat breaks or changes if you apply it
Audit ProcedureHow to check compliance, step by step
Remediation ProcedureHow to fix it, step by step
Default ValueWhat the setting is out of the box
ReferencesLinks, plus framework mappings (CIS Controls, NIST 800-53, PCI DSS, STIG)

SCAP content adds a severity from a fixed set (unknown, info, low, medium, high), a plain description for non-experts beside the rationale, and a per-rule idempotent remediation script. verified ManageEngine's rule row shows the setting, its default, the accepted range, the recommended value, the rationale and a How to Fix column.

Profiles

Level 1 can be implemented promptly without significant performance impact. Level 2 is defence in depth and may have an adverse effect on usability or business operations if applied without due care. The STIG profile replaces the former Level 3. verified In SCAP terms a profile is a selection of rules: rules are unselected by default, one rule can belong to many profiles, and a profile can override a rule's severity. verified Our Benchmark Profile field (L1 / L2) is correct and should filter which rules attach.

Identity and versioning: the tags question

  • There is no standard numbering convention. A recommendation number is meaningful only inside one benchmark version and can be reused after a check is deprecated.
  • In ComplianceAsCode a rule's unique ID is its own identifier and links it to its checks and fixes. CIS numbers and STIG IDs are references keyed to one product version (cis@ubuntu2204), so the same rule carries a different CIS number on each OS version. verified
  • Corrected: the run first extracted that a CCE is the single global identifier for a rule. All three votes refuted it. CCEs are product-dependent too, a different CCE per product and version. refuted No identifier survives across products.
  • Tenable and Rapid7 both key overrides to the individual rule inside a policy. verified

Data model to design against. A Rule carries our own ID per OS version, the CIS number, the benchmark version, optional CCE and XCCDF IDs, tags, and framework references. Tags are labels many rules share. They are good for filtering and never for identity. The hunch that the tags are the unique identifier is the one thing to drop.

When CIS ships a new version

There is no cadence to design a calendar around. Microsoft's Intune pattern is the best UX reference: when a new baseline version ships, existing profiles become read-only until you choose Update version, and you review the settings diff before updating. A new benchmark version should never silently change a policy. Show that a new version is available, offer a diff of added, changed and removed rules, and let the admin re-pin.

Framework mappings

Mappings to NIST, PCI, HIPAA and STIG arrive with the rule content; ServiceNow imports authoritative sources and citations from the scanner. Tanium covers CIS, NIS2, CMMC and Essential Eight. SolarWinds NCM ships DISA STIG, PCI, HIPAA and SOX reports for network devices. verified They are read-only metadata on a rule, surfaced as chips and as a report axis.

4. The full flow, stage by stage

Every competitor runs one loop. Stages 1 to 4 exist in our module today; 5 to 8 are the gap.

  1. Rule catalogue (vendor-maintained CIS content)
  2. Benchmark, tailored from a CIS parent
  3. Policy: benchmark, targets, schedule
  4. Assessment run
  5. Results: endpoint by rule, with a score
  6. Remediation, then re-assess (back to 4)
  7. Exception: rule by hosts, reason, approval, expiry (feeds back into 5)
  8. Drift detection (continuous) and evidence export

Stages 6 and 7 both loop back: a fix returns to a new run, an exception changes how a result reads.

Catalogue to benchmark

ManageEngine policies are collections of CIS-derived rules grouped by platform. Policies are not targeted directly: you build a Policy Group, pick the platform, select CIS policies into it, then map target groups. Custom policies are made by importing and editing rules, then publishing. verified NinjaOne lets an admin tailor any included benchmark inside the web console while configuring the endpoint scan. CIS WorkBench tailoring forks a published benchmark, changes recommendations and exports it. Practitioners say tailoring is expected practice but should never be ad hoc or undocumented, and different server roles should get separate baseline profiles. In SolarWinds NCM rules roll up into policies and policies into policy reports; one policy can appear in several reports. verified

Ours: Benchmark matches this. Add a lineage line on a custom benchmark (based on CIS Ubuntu 22.04 v2.0.0), a diff against its CIS parent, and a documented reason on each excluded rule, which later seeds the exception record.

Benchmark to policy to assessment

ManageEngine maps target systems, schedules audits, and shows compliance percentage and violated rules per policy. Tanium imports content into Comply, runs an assessment, pushes CIS remediation in Enforce keyed to the same control IDs, then re-runs the assessment to verify. verified CIS recommends testing any benchmark in a non-production environment first, and DISA STIG groups controls by severity CAT I, II and III.

Ours: Policy matches this. Add a pilot or test-group stage, and store the benchmark version with every run.

Results and scoring

ManageEngine scores compliance as a percentage per computer, per target group and per policy. NCM reports node by rule pass or fail. verified ServiceNow does not calculate results itself; it imports them by state, Passed and Skipped against Failed, Warning, Error and Unknown, and logs unmatched assets to a missing-asset table. verified Tenable's Change Result rules flip a failed host-audit check to Passed, or back, when a fix was made in a way the scan cannot detect; that changes the asset's compliance percentage and the override and its justification are kept on the rule. verified

Status vocabulary to adopt: Pass · Fail · Manual (needs a human) · Not applicable · Error or Unknown · Excepted. Score = passed ÷ (passed + failed), with excepted and not-applicable excluded and the denominator stated beside the number. Three roll-ups: endpoint, policy, benchmark.

Remediation and the ITSM join

ServiceNow groups failed test results into Remediation Tasks by rules with up to six grouping keys; a default rule keyed on Assignment group plus Test ships disabled; one result can belong to several tasks; task assignment rolls down to its results. verified From a task you Create Change, choosing all active results or a filtered set; the CIs join the change's Affected CIs and the results move to Awaiting Implementation; the task resolves when its linked changes resolve; the change can be Emergency, Normal or Standard. verified Tanium pivots from a Comply finding into Enforce or native Patch and Deploy, verified back in Comply. ManageEngine shows guidance only: summary, rationale and step-by-step fix per violation. Automox has no CIS catalogue; each Worklet carries its own evaluation block and remediation block attached to device groups.

Ours: nothing here yet. From a failed rule on N endpoints, offer three doors: Create Change with affected CIs attached, Deploy fix as a Patch or Package deployment seeded with the endpoints, and Assign task grouped by rule rather than one ticket per endpoint. Each door writes a status back on the result, and a re-assessment closes it.

Exceptions and waivers

What every product agrees on:

  • Scope is a rule and a host set. Qualys exempts certain hosts from controls in a policy. verified Rapid7 overrides one rule at a time, never a group, and the scope depends on where you start: the Policies view covers all assets, the Scanned Assets view adds this asset only and this asset until the next scan. verified ServiceNow scopes an exception to a whole remediation task, so individual results inside it cannot be tracked. unverified
  • A reason is mandatory everywhere. "No known exploits" alone is not a valid justification. unverified
  • Approval is routed. Rapid7 separates submit, review and delete permissions. verified Qualys VMDR for ITSM routes through approver groups, any member can approve, some requests pass three or four stages, a rejection needs a comment, and approvers work from a Pending My Approval queue. verified ServiceNow can be two-level, and an exception cannot be requested if no first-level approver is configured. unverified
  • Expiry is standard. Tenable Accept rules carry a mandatory justification and an expiration unverified; UC Irvine caps accept and recast at one year unverified; Rapid7 reviewers can set an expiry on approval. Practitioner field lists add a next review date, compensating controls and a change-control reference, and say to keep expired exceptions visible until resolved.
  • Two kinds exist. Tenable.sc separates Accepted Risk, left unfixed at the reported severity, from Recast Risk, where the severity is changed because the organisation disagrees; false positives are labelled recast after verification. unverified
  • Raw results stay untouched. Overlay rules never modify scan data, and Rapid7 writes overrides and reasons into the XCCDF export used for certification review. verified
  • The work item follows the exception. ServiceNow's task is In review while pending, Deferred on approval, back to its previous state on rejection, and back to Open when the exception expires. unverified

Record to design. An Exception carries the rule ID, benchmark version, endpoints or all, a kind (accepted risk, false positive, compensating control), reason, risk level, compensating controls, owner, approvers, an optional change reference, expires-on, next review, and a status of requested, approved, rejected or expired. The raw result stays Fail; the view shows Excepted with the reason on hover; expiry re-opens the finding.

Drift, re-scan and evidence

Run benchmarking as a continuous control check, not a one-time assessment. Check for drift after emergency changes, admin access, platform upgrades and automated repairs, and send unapproved changes to an owner rather than overwriting them. Each policy in an Intune baseline has its own Fix drift action, so one policy can be remediated without republishing the whole baseline, and a drifted policy can be rolled back to its assigned version. Evidence is the scan output, the system state and a log trail operators cannot alter; store the benchmark version with each result so an auditor can re-run and reproduce.

Ours: scans exist, drift does not. Add compliant-since and drifted-on per endpoint and rule, a drift filter on a policy's results, and an export that carries benchmark version, scope, timestamp and exceptions.

6. Recommendations for our module

Twelve changes, grouped by screen. Keep one word per thing: Rule · Benchmark · Policy · Assessment (a run) · Result (endpoint by rule) · Finding (a failed result) · Exception. Do not use violation and finding for the same thing.

Admin › Rules

  1. Show a rule's detail in CIS field order, with Assessment Status, Profile and Severity as pills and framework mappings as chips.
  2. Make our own ID per OS version the rule's identity. Show the CIS number as "CIS 5.2.5 in Ubuntu 22.04 v2.0.0". Tags stay tags.

Admin › Benchmark

  1. Put a lineage line on custom benchmarks ("Based on …"), a diff view against the parent, and a required reason on each excluded rule.
  2. Pin versions. A policy pins a benchmark version; a new CIS version shows as "update available" with a rule diff and is never applied silently.
  3. Add a profile filter on Attach Rules (L1 / L2 / STIG). The field already exists.

Technician › Compliance Policy

  1. Add a pilot group before fleet rollout, and store the benchmark version on every run.
  2. Build a Results tab with the six-state vocabulary, a score with its denominator stated, three roll-ups, severity on each failed rule, and the rule's Remediation Procedure inline on the finding.
  3. Put three remediation doors on a finding: Create Change (affected CIs attached), Deploy fix (Patch or Package with the endpoints seeded), Assign task (grouped by rule). Status writes back; a re-assessment closes it.
  4. Make exceptions records: request from a finding, an approver queue for the security admin, expiry that re-opens the finding, and an exportable exception register.
  5. Add drift: compliant-since and drifted-on per endpoint and rule, a drift filter, and Fix drift per rule.
  6. Add an evidence export per run: benchmark version, scope, timestamp, results, and exceptions with reasons.

Visualization (exists)

  1. Confirm with the product what the posture bands and the 85% target mean. Competitors score percentages without a universal target, so the target should be a tenant setting.

7. Confidence and caveats

24 of the 97 claims went through three-vote verification (the run caps at 25). 20 came back supported by all three votes, 2 were refuted, and 4 never got their votes because the session ended. The other 73 claims are extraction only; trust them by their source quality below.

  • Refuted: that a CCE is the single global identifier for a rule (CCEs are per product and version), and that rule content in products has to follow a regular release cadence (CIS has no fixed schedule; only the monthly announcement email is regular).
  • Unverified: everything from the UC Irvine Tenable.sc governance page, the Tenable Accept-rule details, and ServiceNow's exception lifecycle.
  • Source quality: 15 of the 22 sources are primary vendor documentation (CIS, Qualys, Rapid7, Tenable, ServiceNow, ManageEngine, Tanium, SolarWinds, ComplianceAsCode). IBM's deck is secondary. nhimg, oneuptime, natsar and Nerdio are blogs. The THWACK forum thread and the CIS Atlassian KB page were fetched but rated unreliable or came back empty; the numbering-convention point comes from the search snippet of that KB page, not from a fetch.
  • Not covered by the run: pricing, agent architecture, how competitors present Manual checks in the UI, and any usability research on compliance consoles. A second, narrower run on Manual-check UX and exception-register UX is worth it if those become design questions.
