What compliance is, and why an IT service desk needs it

No technical background needed. Each part has a picture you can point at while you explain it to someone else.

1Start with the idea

Every computer has hundreds of settings: how long a password must be, whether the screen locks when you walk away, whether a guest can log in without a password, whether an old and risky feature is switched on. Most of those settings arrive in whatever state the manufacturer chose, and that state is often convenient rather than safe.

Compliance means two things at once: the computer's settings match an agreed safe standard, and you can prove it to someone who asks.

In plain words

Think of a fire-safety inspection for a building. There is a written code (the standard), an inspector walks every floor with a checklist (the scan), each item passes or fails (the result), the building manager fixes what failed (remediation), and the signed report goes in a file for the authorities (the evidence).

Compliance does exactly that, for computers instead of buildings.

2Who is CIS, and why do they write the standard?

CIS is the Center for Internet Security, a non-profit organisation. Thousands of security experts from companies, governments and universities around the world volunteer there. For each operating system and major product, they argue it out and agree on a list of safe settings. When they reach agreement, CIS publishes the list. That agreement process is why companies trust it: no single vendor wrote it.

The published list for one product is called a CIS Benchmark. There is one for Windows 11, one for Windows Server 2022, one for Ubuntu 22.04, one for Cisco switches, one for Microsoft 365, and so on. The benchmark is free to read as a PDF. The machine-readable version that scanners use is sold to software vendors through a membership, which is why products like ours ship CIS content rather than asking customers to write their own.

Why not just write our own rules?

A company could, but then every auditor and every customer would ask "says who?". CIS is the answer everyone already accepts. Regulations for card payments (PCI DSS), for health data (HIPAA) and for government systems all point at CIS or something equivalent. Using CIS means the hard argument about what "safe" means has already been had by people whose job it is.

3What is a rule?

A benchmark is a long checklist. Each line on it is a rule (CIS calls it a recommendation). A rule is one specific setting and the safe value for it. The Windows 11 benchmark has several hundred rules; Ubuntu's has about the same.

Every rule is written the same way, and that structure is what our product shows on a rule's detail page. Here is a real one, in plain words:

CIS Windows 11 · rule 2.3.7.3 · Level 1 · Automated
Lock the screen after 15 minutes of inactivity
What
The computer must lock itself when nobody has touched it for 15 minutes or less.
Why
Someone walking past an unlocked, unattended computer can read or change anything the signed-in person could.
What it costs
People who step away briefly have to type their password again when they return.
How to check
Open the security policy and read the inactivity limit. If it is 0 or above 900 seconds, the rule fails.
How to fix
Set the inactivity limit to 900 seconds or less, either by hand or by pushing a setting to every computer at once.

Three labels on every rule matter for the design:

  • Level 1 or Level 2. Level 1 rules are safe to apply everywhere and rarely break anything. Level 2 rules are stricter and can get in people's way, so they are for places where security matters more than convenience, such as a server room or a bank. Level 2 includes everything in Level 1 and adds more.
  • Automated or Manual. Automated means a scanner can check it by itself. Manual means a person has to look, for example "the data centre door has a lock". Our product can only score the automated ones.
  • Severity. How bad it is if the rule fails. A weak password rule is high; a cosmetic setting is low.
One thing to get right in the product

The rule's number, like 2.3.7.3, is only meaningful inside one benchmark. The same rule can have a different number in the Windows 10 benchmark, and numbers get reused when CIS retires a rule. Tags are labels that many rules share. So neither the number nor the tags can be the rule's identity. The product needs its own ID for each rule in each operating system version, and shows the CIS number and the tags as information beside it.

Why one benchmark per operating system version? Because the settings genuinely differ. Windows 11 has settings Windows 10 never had, and the safe value for a Linux setting is a different file on a different version. That is also why our Benchmark screen locks a benchmark to one Type and one OS version, and only offers that version's rules.

Why "tailored"? No company applies a CIS benchmark exactly as published. A rule might break an application the business depends on, so the security admin removes it from the company's copy and writes down why. That company copy, based on the CIS original, is the benchmark a policy actually uses.

5Why does an IT service desk (ITSM) need this?

Dedicated security scanners already exist. The reason compliance belongs inside ServiceOps is that a failed rule is not useful until somebody fixes it, and fixing is what a service desk already does all day.

Four reasons, in the order a manager would give them:

  1. Attackers look for wrong settings first. Most break-ins start with a setting left in its convenient default, not with clever code. Compliance closes those doors before anyone tries them.
  2. Someone will ask for proof. A payment-card auditor, a health regulator, a big customer's security questionnaire, or cyber-insurance. "We think we are fine" is not an answer. A dated report that says which computers passed which rules is.
  3. The desk already owns the fix. The same technicians, the same change approval, the same patch and package tools. Without the join, a security team emails a spreadsheet of failures and the desk re-types it into tickets.
  4. Settings drift. A technician relaxes a setting while troubleshooting and forgets to put it back. A new laptop arrives set up differently. Only a repeated check catches that.

6The two people, and what each one does

Our module has two users on purpose. They are different jobs with different knowledge.

The hospital version

The infection-control officer writes the hygiene rules for the whole hospital and decides when a ward may skip one. Ward staff follow the rules every shift, report what they could not do, and ask for a documented exception when a patient's situation makes a rule impossible.

A third person never edits anything but reads everything: the auditor. They want to see the score, the history, and every exception with its reason and its approver.

8A worked example you can retell

Follow one laptop through the loop.

  1. Priya in Finance has a Windows 11 laptop. It is in the company's asset list, so ServiceOps already knows it exists.
  2. The security admin built a benchmark called Windows 11 Laptops, Level 1 from the CIS original. She removed one rule about USB storage because Finance needs USB drives for the bank's token, and wrote that reason down.
  3. A technician created a policy: that benchmark, all 300 Windows 11 laptops, every Sunday night.
  4. Sunday's scan checks 280 rules on each laptop. Priya's laptop fails two: the screen-lock timeout is 30 minutes instead of 15 Fail, and an old file-sharing protocol is still enabled Fail. The other 278 pass Pass. Her laptop scores 99%; the policy scores 91% across all 300.
  5. The technician opens the screen-lock failure. 120 laptops have the same problem. She clicks Deploy fix, which creates one package deployment to all 120, instead of 120 tickets.
  6. The file-sharing failure is different: Finance's old printer needs that protocol. The technician clicks Request exception: this rule, Finance's 12 laptops, reason "legacy printer, replacement ordered", expiry in 90 days.
  7. The security admin sees the request in her approval queue and approves it. Those 12 results now show Excepted instead of Fail, with the reason on hover. The raw result still says Fail underneath, so nothing is hidden from an auditor.
  8. Next Sunday's scan runs. Screen lock now passes on all 120. The policy score is 97%. In 90 days the exception expires and the file-sharing failure comes back on its own, so nobody has to remember.
  9. In March the auditor asks for proof. The admin exports the policy's report: benchmark version, which laptops, the date of each scan, every result, and the exception register with reasons and approvers.
